Prepared, awaiting activation.

The update checks approved, verified GitHub email addresses and repository write access. Thirteen authentication tests passed. The OAuth application, authentication Worker, repository update, and second person's repository access still need to be connected.

1. Give the second administrator repository access

  1. Open the repository's Collaborators settings.
  2. Choose Add people, enter the exact email supplied for the second administrator, and send the invitation to that address or its confirmed GitHub account.
  3. The recipient accepts the invitation and verifies that same email in GitHub email settings.

Your account macv0223 already owns this repository. The second person receives collaborator access in GitHub and administrator access in the PTO editor after successful verification. These are separate roles.

2. Upload the sign-in update

  1. Extract the update ZIP and open repository-update.
  2. In the repository, choose Add file → Upload files.
  3. Drag the folders cms, public, tests, and docs from inside repository-update into the upload area. Preserve their folder paths.
  4. Commit the update to main. The existing publication workflow rebuilds the website.

The update changes the sign-in service and administrator restoration check. The site remains in its awaiting-setup state until the authentication origin is configured.

3. Create the small sign-in service

  1. Open Cloudflare, then sign in or create an account.
  2. Go to Workers & Pages → Create application → Create Worker. Name the Worker thrive-pto-auth and deploy it.
  3. Choose Edit code. Open worker.txt from the update ZIP in a text editor, copy its complete contents, and replace the starter Worker code.
  4. Deploy the code and copy the Worker's assigned HTTPS address. This is your Worker origin, for example https://thrive-pto-auth.YOUR-SUBDOMAIN.workers.dev.

It is normal for the service to report that authentication is not configured until its settings and secrets are added.

4. Register GitHub sign-in

Open GitHub's new OAuth application page and enter:

FieldValue
Application nameThrive PTO editor
Homepage URLhttps://macv0223.github.io/thrive-pto/
Authorization callback URLYour Worker origin followed by /callback

If GitHub shows Expire user access tokens, uncheck it for this direct Decap integration, which does not implement refresh-token handling. Device flow is not used.

Register the application, note its Client ID, and generate a Client secret. Enter these directly into Cloudflare in the next step.

5. Set the Worker variables and secrets

Open your Worker → Settings → Variables and Secrets → Add. Use the exact key names below, then deploy the settings.

NameTypeValue
CMS_ORIGINTexthttps://macv0223.github.io — the origin only, without the repository path or a trailing slash
AUTH_ORIGINTextYour exact Worker HTTPS origin, without a trailing slash
REPOSITORYTextmacv0223/thrive-pto
PRIVATE_REPOSITORYTextfalse
ALLOWED_ADMIN_EMAILSSecretThe two approved administrator emails, separated by a comma. Use the exact addresses supplied in the conversation.
GITHUB_CLIENT_IDSecretThe OAuth application's Client ID
GITHUB_CLIENT_SECRETSecretThe OAuth application's Client secret
SESSION_SECRETSecretA new random 64-character hexadecimal value. You can generate one below.

Leave ALLOWED_USERS unset for an administrator-only workspace. This keeps authorization restricted to verified matches from ALLOWED_ADMIN_EMAILS.

The generator uses your browser's cryptographic randomness. Copy the value directly into the Cloudflare SESSION_SECRET secret.

Client secrets and the session secret belong in Cloudflare's Secret fields. They should not be pasted into chat or committed to the public repository.

6. Connect the website to the sign-in service

  1. Open the repository's Settings → Secrets and variables → Actions → Variables.
  2. Add a repository variable named CMS_OAUTH_ORIGIN with your exact Worker HTTPS origin as its value.
  3. Open Actions → Publish PTO website → Run workflow, choose main, and run it.
  4. Wait for successful build and deployment, then open the PTO editor workspace.

7. Sign in and verify both accounts

  1. Click Sign in to edit with GitHub. Complete GitHub authentication and authorize the requested repository and email-read access.
  2. Confirm you can open a page, change a small piece of text, see its preview, and save a draft.
  3. Publish the draft and check the resulting public page.
  4. Repeat sign-in with the second administrator's own GitHub account after they accept the repository invitation.
  5. Check administrator content history and create a restoration draft only for a revision you intend to review. The live site changes when that draft is merged.

An unverified or different email is denied. An approved email without repository write access is also denied. The addresses are checked by the authentication service, rather than accepted from a typed email field.
